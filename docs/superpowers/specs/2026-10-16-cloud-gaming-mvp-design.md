# Облачный гейминг — дизайн MVP

Дата: 2026-10-16. Статус: черновик на согласование.

Пометка **[моё решение]** — выбор, сделанный при проектировании, а не владельцем продукта; его можно оспорить. Всё без пометки — решено владельцем.

## 1. Зачем

Платный сервис облачного гейминга в браузере. Пользователь привязывает свой Steam, видит свою библиотеку в интерфейсе в духе GameHub (macOS), нажимает «Играть» — и через минуту играет в браузере, без установки и без мощного железа. Игры принадлежат пользователю (его Steam-аккаунт), сервис даёт железо и стрим.

MVP нужен, чтобы на домашнем сервере `brofrong` получить работающий продукт целиком (сайт → сессия → игра → учёт времени → админка) на той же кодовой базе, которая потом поедет в арендованный дата-центр Selectel.

## 2. Цели, не-цели, анти-цели

**Цели MVP**
- Вход на сайт через Steam, библиотека пользователя с оценкой совместимости из ProtonDB.
- «Играть» → игра стримится в браузер; после первого входа в Steam интерфейс Steam пользователь не видит — сразу игра.
- Игры, которых нет в хранилище, скачиваются автоматически с прогрессом на сайте.
- Учёт реально сыгранного времени (основа будущей оплаты).
- Правила простоя и отключения с настраиваемыми таймаутами.
- Админка: воркеры (подключаются как агенты, в духе Arcane), живые сессии и потребление ресурсов, статистика и «стоимость» игр, настройки.
- Несколько лёгких игр на одной GPU по измеренной стоимости.
- Архитектура распределённая с первого дня (оркестратор, агенты, хранилище — отдельные сервисы), даже если в MVP всё стоит на одной машине.

**Не-цели MVP** (этап 2 и позже): оплата; Epic Games; provisioner (автонастройка серверов по SSH); развёртывание в Selectel; TURN/coturn (не нужен, см. §9); мобильные приложения; игры с античитом; Windows-VM; несколько дата-центров.

**Анти-цели** (провал, даже если «работает»)
- Храним пароли Steam или видим их. Вход в Steam — только QR/Steam Guard внутри стрима.
- Пользователь теряет сохранения.
- Пользователь платит (учитывается время) за очередь, установку, загрузку Steam, синхронизацию сохранений.
- MVP ломает или нагружает чужие сервисы на `brofrong` (Immich, Plex, Vaultwarden, Pocket ID и ещё ~35 контейнеров).
- Код, привязанный к одной машине, который придётся переписывать для дата-центра.

Юридический риск модели «как GeForce Now без договоров с издателями» владелец знает и принял.

## 3. Пользовательский путь

1. **Вход на сайт** через Steam OpenID → получаем SteamID → создаём пользователя.
2. **Библиотека**: Steam Web API `GetOwnedGames`. Если профиль приватный — экран с инструкцией открыть «Сведения об играх». У каждой игры — плашка ProtonDB (Platinum/Gold/Silver/Bronze/Borked) с человеческой подписью («работает идеально» … «скорее всего не запустится»).
3. **«Играть»** → экран статусов: «В очереди» → «Устанавливаем 34 %» (если игры нет в хранилище) → «Запускаем» → стрим.
4. **Первый запуск**: в стриме открывается только окно входа Steam, пользователь сканирует QR в мобильном Steam. Сессия Steam сохраняется в его профиль (§7.4). Дальше — всегда сразу игра.
5. **Игра**: полноэкранный плеер, геймпад/клавиатура/мышь, звук.
6. **Выход из игры** → «Сохраняем прогресс…» (ждём облако Steam и выгрузку профиля) → назад в библиотеку с итогом «вы играли 1 ч 12 мин».

## 4. Компоненты

```
             Браузер (SPA: сайт + плеер + админка)
                │ HTTPS/WSS (Effect RPC)        ▲ WebRTC UDP (видео/звук/ввод)
                ▼                               │
        ┌───────────────┐   WS (Effect RPC)  ┌──┴──────────────── Воркер ──────────┐
        │ api           │◄──────────────────►│ agent ── Docker ──► session-контейнер│
        │ (+ auth, RPC, │                    │   │  (Steam+Proton+Selkies+NVENC)    │
        │ signaling-    │                    │   └─ overlayfs(gamestore:ro + rw)    │
        │ прокси)       │                    └──────────────────────────────────────┘
        ├───────────────┤                    ┌──────────── Gamestore ──────────────┐
        │ orchestrator  │◄──────────────────►│ agent(role=gamestore) ── installer   │
        └──────┬────────┘                    │ NFS-экспорт библиотеки игр           │
               │                             └──────────────────────────────────────┘
        PostgreSQL · RustFS (профили пользователей)
```

- **web** — React SPA: сайт, плеер, админка.
- **api** — публичный HTTP/WS: Better Auth, Effect RPC для фронта, прокси сигналинга к сессиям, стримы статусов.
- **orchestrator** — жизненный цикл сессий, планировщик, фоновые задачи (установки, таймауты, агрегация метрик). Держит соединения с агентами. **[моё решение]**: отдельный процесс от api, общается с ним через Postgres и внутренний RPC; можно запустить в одном процессе на старте, но границы модулей — как у отдельных сервисов.
- **agent** — один бинарь, роли `worker` и/или `gamestore`. Сам подключается к оркестратору по WebSocket (исходящее соединение, без открытых портов). На worker: запуск/остановка session-контейнеров, overlayfs, профили, метрики GPU/CPU/RAM по процессам, детект процесса игры, синхронизация облака. На gamestore: installer, место на дисках, список установленных игр.
- **session image** — образ сессии (§9).
- **PostgreSQL** — всё состояние. **RustFS** — профили пользователей (S3).

## 6. Сессия: состояния и время

Состояния (**[моё решение]** по названиям, логика согласована):

| Состояние | Что происходит | Время учитывается |
|---|---|---|
| `queued` | ждём ёмкость на воркере | нет |
| `installing` | игры нет в хранилище — installer качает (§8) | нет |
| `starting` | контейнер, восстановление профиля, старт Steam, `-applaunch` | нет |
| `playing` | процесс игры жив | **да** |
| `idle_warning` | N минут без ввода → «Вы ещё здесь?»; нет ответа M минут → `stopping` | **да** (простой — игровое время) |
| `disconnected` | вкладка закрыта/сеть пропала, игра продолжает работать; вернулся за K минут → `playing` | **да, если вернулся; нет, если нет** **[моё решение]** |
| `stopping` | игра закрыта/выкинули: ждём выгрузку облака Steam, выгружаем профиль, гасим контейнер | нет |
| `ended` / `failed` | итог | — |

Значения по умолчанию: N = 15, M = 2, K = 5 минут. Все — в настройках админки (§11), применяются на лету, в том числе к уже идущим таймерам.

**Учёт времени.** Агент находит процесс игры (Steam запускает его через `reaper SteamLaunch AppId=<id>`), шлёт heartbeat раз в 30 с; оркестратор пишет отрезки в `play_segments` (начало, конец, тип). Падение воркера теряет ≤ 30 с. Оплата в будущем — просто чтение отрезков.

**Простой и отключение** **[моё решение]**: плеер в браузере знает время последнего ввода и шлёт его в heartbeat по нашему RPC-соединению; отключение = пропал наш WS **и** WebRTC-пир. Решение принимает оркестратор, а не браузер.

Пользователь может держать только одну активную сессию (ограничение Steam: одна игра на аккаунт одновременно). Установка — часть этой же сессии (состояние `installing`), а не отдельное действие, поэтому профиль пользователя в каждый момент используется ровно одним процессом: installer и игровая сессия никогда не держат его одновременно. Профиль в RustFS версионируется; выгрузка с устаревшей версией отклоняется **[моё решение]**.

## 7. Steam

### 7.1 Вход на сайт
Steam — это OpenID 2.0, не OAuth: в Better Auth нужен свой провайдер/плагин. **Проверить первым делом.** Нужен ключ Steam Web API.

### 7.2 Библиотека и ProtonDB
`GetOwnedGames` с `include_appinfo`. Кэш в БД, обновление при входе и по кнопке. ProtonDB: неофициальный JSON по appid (`/api/v1/reports/summaries/<appid>.json`), кэш в БД, обновление раз в сутки, недоступность ProtonDB не ломает библиотеку.

### 7.3 Запуск сразу в игру (проверено спайком)
Внутри сессии: `steam -silent -applaunch <appid>` в окружении графической сессии **с LD_PRELOAD интерпозера ввода Selkies** (иначе Steam не видит геймпад). С тёплым профилем Steam входит сам (~1 с), игра поднялась за 37 с от холодного старта контейнера.

### 7.4 Профиль пользователя
Профиль = всё, что нужно, чтобы Steam вошёл сам и сохранения не потерялись:
- конфиг и токены Steam (`config/`, `userdata/`, `~/.steam/registry.vdf`, `loginusers.vdf`);
- сохранения игр вне Steam Cloud: `~/.config/…` (так хранит Vampire Survivors), `compatdata/<appid>/pfx/drive_c/users/steamuser` у Proton-игр.

Хранение: зашифрованный архив в RustFS (ключ сервиса из секрета, шифрование на стороне агента). Восстанавливаем перед стартом, выгружаем в `stopping`. Профиль переживает смену воркера. Бинарники Steam и рантайм в профиль **не** входят — они в образе (иначе 6,5 ГБ на пользователя). Точный whitelist путей и формат архива — на строителе.

Если токен Steam протух — сессия показывает QR-вход в стриме, как в первый раз.

### 7.5 Облачные сохранения (проверено спайком)
Работают штатно. Маркер завершения выгрузки — строка `[AppID <id>] Upload complete, result OK` в `~/.local/share/Steam/logs/cloud_log.txt` (≈5 с после выхода). Агент ждёт этот маркер (с таймаутом) перед уничтожением контейнера. Конфликт сохранений Steam показывает сам — пользователь видит его в стриме.

## 8. Хранилище игр (gamestore) и установка

- Одна библиотека Steam на gamestore-сервере, раздаётся воркерам по NFS v4.2. В MVP gamestore и воркер — одна машина (`brofrong`, массив из 4×4 ТБ HDD), NFS всё равно используется, чтобы схема совпадала с продом. Настройка массива/NFS в MVP — руками (provisioner — этап 2).
- **Сессия никогда не пишет в общую библиотеку.** Агент собирает overlayfs: lower = библиотека (ro), upper = личный слой сессии на локальном диске воркера, merged монтируется в контейнер как библиотека Steam. Upper удаляется после сессии. Нужно, потому что игры пишут в свою папку (Vampire Survivors пишет `LastRunBackup.sav`) и Steam хочет писать манифесты.
- **Установка**: installer — тот же session image в режиме установки на gamestore-хосте, библиотека смонтирована rw, профиль пользователя восстановлен (игру качает Steam пользователя — он ею владеет). Прогресс читаем из `appmanifest_<appid>.acf` и стримим на сайт. Одна игра — один процесс установки (single-flight по appid); второй желающий ждёт тот же job. После установки профиль выгружается обратно, сессия продолжается на воркере.
- **Обновления игр** перед стартом сессии делает тот же installer, если `buildid` в библиотеке устарел. Как надёжно заставить Steam внутри сессии не обновлять игру в upper-слой — на строителе (риск, см. §14).
- **Если overlayfs со Steam не заработает** (первая задача MVP — проверить): запасной вариант **[моё решение]** — копия папки игры на локальный NVMe воркера на время сессии (reflink, где ФС умеет, иначе обычная копия, с кэшем популярных игр). Остальная архитектура от этого не меняется: меняется только то, как агент готовит библиотеку для контейнера.

## 9. Образ сессии и стрим (выводы спайка)

База: `ghcr.io/selkies-project/selkies-egl-desktop:26.04` (Selkies 2.0, KDE). Рабочий конфиг — `spike/compose.yaml` и `spike/Dockerfile`. Обязательные настройки:

| Что | Значение | Почему |
|---|---|---|
| Транспорт | `SELKIES_MODE=webrtc` | по умолчанию `websockets` (TCP) — в прошлых тестах давал лаги и плохое качество |
| Сеть | `SELKIES_WEBRTC_UDP_MUX_PORT=<порт сессии>`, `SELKIES_WEBRTC_PUBLIC_IP=<IP воркера>`, `SELKIES_WEBRTC_ICE_LITE=true` | один UDP-порт на сессию, прямое соединение, TURN не нужен |
| Захват | `SELKIES_WAYLAND=true` → «Wayland · zero-copy» | X11 копирует каждый кадр через CPU |
| Кодирование | `SELKIES_ENCODER=h264enc` (уходит в NVENC), CBR, старт 10 Мбит/с, 60 fps | |
| Ключевые кадры | `SELKIES_KEYFRAME_INTERVAL=2` | при `0` одна потеря пакетов замораживает картинку |
| HTTPS/auth Selkies | выключены, веб-порт Selkies наружу не публикуется | доступ только через наш api (§10) |

Требования к воркеру (проверены на `brofrong`):
- `nvidia-drm modeset=1` на хосте (иначе нет GBM → нет zero-copy);
- в образ/контейнер добавить 32-битные библиотеки NVIDIA **той же версии, что драйвер хоста** (клиент Steam 32-битный, toolkit их не прокидывает) — образ собирается под версию драйвера (`cg-session:<driver>`);
- на Debian пробросить `libnvidia-allocator` (GBM-бэкенд) — toolkit не находит его в `nvidia/current/`;
- GPU с NVENC (не A100/H100).

Замеры спайка через интернет: 60 fps, захват→кодирование ~1,4 мс, кодирование ~5 мс. У клиента с нестабильной сетью были потери — отсюда требования MVP: **адаптивный битрейт** (снижать при потерях) и **индикатор «нестабильное соединение»** в плеере. Как реализовать адаптацию (настройки Selkies/pacer или свой контур по статистике WebRTC) — на строителе.

**Порты на воркере** **[моё решение]**: у каждой сессии слот `i`: UDP `59000+i` публикуется наружу, веб-порт Selkies — только на loopback/внутреннюю сеть, к нему ходит наш api. Контейнеры сессий — в bridge-сети (а не host, как в спайке), чтобы изолировать порты; публичный IP объявляется через `SELKIES_WEBRTC_PUBLIC_IP`. На `brofrong` входящий UDP из интернета доходит напрямую (проверено на 59000).

Геймпад: Selkies отдаёт DualSense и др. как виртуальный Xbox 360 через интерпозер — Steam видит (проверено). Тачпад/гироскоп/адаптивные триггеры не передаются — ок для MVP.

## 10. Плеер и доступ к стриму

Свой плеер на React вокруг клиентской части Selkies 2.0 (её JS-ядро), без их UI-панели. Браузер не ходит в контейнер напрямую: сигналинг (WebSocket) идёт через наш api, который проверяет, что сессия принадлежит пользователю, и проксирует к Selkies нужного контейнера. Медиа — напрямую браузер ↔ воркер по UDP. Как именно встраивать клиент Selkies (пакет, форк, вендоринг) — на строителе.

## 11. Админка

Вход только через Pocket ID (OIDC через SSO-плагин Better Auth), роль `admin` по группе в Pocket ID. Игроки в админку не попадают.

- **Воркеры**: «Добавить воркер» → одноразовый токен и готовая команда `docker run … agent --token=…`. Агент подключается, сообщает железо (GPU, VRAM, драйвер, CPU, RAM, диски), появляется как «ожидает подтверждения» → админ подтверждает. Режим drain (не брать новые сессии). Живой статус.
- **Сессии**: список активных — пользователь, игра, воркер/GPU, состояние, длительность, потребление GPU/VRAM/CPU/RAM в реальном времени; принудительно завершить.
- **Игры**: измеренная стоимость, статистика сессий, ручное переопределение стоимости, ProtonDB-тир.
- **Gamestore**: место, список установленных игр с размерами, удалить игру.
- **Настройки**: N/M/K таймауты, битрейт по умолчанию и т.п. Типизированы (Effect Schema), у каждой — дефолт и допустимый диапазон, применяются на лету.

Ориентир по UX — Arcane (docker-менеджер), он стоит на `brofrong`.

## 12. Планировщик и стоимость игр

- Ёмкость воркера — по каждой GPU: VRAM, загрузка GPU, сессии NVENC; плюс CPU и RAM машины.
- Стоимость игры — в тех же единицах. Нет данных → игра «тяжёлая», занимает GPU целиком **[моё решение]**.
- Агент снимает потребление по процессам сессии (NVML по PID для GPU/VRAM/энкодера, cgroups для CPU/RAM) раз в несколько секунд; оркестратор хранит сэмплы и считает стоимость как p95 по последним сессиям + запас. Админ может переопределить.
- Размещение: первая GPU, куда влезает (стоимость ≤ свободной ёмкости); иначе очередь. Жёсткие лимиты CPU/RAM каждому контейнеру.
- Параметры по умолчанию **[моё решение]**: авто-стоимость появляется после ≥ 3 сессий игры; считается по сэмплам только из состояния `playing`, без первых 2 минут (загрузка/меню); p95 по последним 20 сессиям; запас +20 %. До этого — «тяжёлая» (вся GPU), поэтому новая игра не может переполнить GPU. Все параметры — в настройках админки.
- Ориентир из спайка: Vampire Survivors — ~17 % GPU и ~45 МБ VRAM у процесса (~270 МБ вся сессия).

## 13. Данные (основные сущности)

Пользователи и аккаунты Better Auth; Steam-профиль (SteamID, ник, аватар); библиотека пользователя (appid, playtime в Steam); игры (appid, название, обложка, ProtonDB-тир и дата, стоимость авто/ручная); gamestore-элементы (appid, статус, размер, buildid); jobs установки (прогресс, ошибка); воркеры (токен-хэш, статус, железо, ёмкость, drain); GPU воркера; сессии (состояние, история переходов, воркер, GPU, слот/порт); `play_segments`; сэмплы потребления; профили (ключ объекта в RustFS, версия, размер); настройки. Точная схема — на строителе.

## 14. Риски и что проверить в первую очередь

1. Steam OpenID в Better Auth (нет готового провайдера).
2. Встраивание клиента Selkies 2.0 в свой плеер и проксирование сигналинга через api.
3. Selkies в bridge-сети с UDP mux и `PUBLIC_IP` (спайк был в host-сети).
4. Steam + overlayfs-библиотека: не обновляет ли игру в upper, не ломает ли манифесты.
5. Installer на профиле пользователя; что делать, если пользователь параллельно играет на другом устройстве.
6. Холодный старт 37 с — цель MVP ≤ 60 с от «Играть» до игры для установленной игры. 37 с в цель укладываются, поэтому пула тёплых контейнеров в MVP нет; вернуться к нему, только если реальные замеры превысят 60 с.
