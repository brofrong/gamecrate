# GameCrate — вход, регистрация и привязка способов входа — дизайн

Дата: 2026-10-22. Статус: реализовано 2026-10-22 (ветка `feat/auth-login-linking`, план
`docs/superpowers/plans/2026-10-22-auth-login-and-linking.md`).

Отклонения от текста ниже при реализации:

- Better Auth 1.7.10 отправляет письмо с кодом в фоне и отвечает 200 даже если SMTP упал; поэтому
  интерфейс показывает «Письмо не пришло? Проверь спам или отправь ещё раз» и открывает «Отправить
  ещё раз» через 30 с; `MAIL_FAILED` — только для ошибок на уровне транспорта (§6.5).
- Id Steam-провайдера в `account.provider_id` — `steam`, а не `steam-openid` (везде, включая SQL
  чистки старых пользователей, §3.5).
- Колонок `steamName`/`steamAvatar` нет — в профиле показан только `SteamID` (§6.4 оставила это
  на решение строителя).
- `/steam/login` закрыт хуком `before` (404 `STEAM_LOGIN_DISABLED`); правило отвязки находит
  аккаунт по `accountId`, как и сам эндпоинт, и никогда не доверяет `body.providerId`; callback
  привязки Pocket ID пишет роль только при успешном редиректе.
- Telegram-callback проверяет тело запроса (400 `TELEGRAM_INVALID_BODY`) и считает `auth_date` в
  будущем просроченным.
- `patches/better-auth-steam@0.2.3.patch` расширен: в флоу привязки плагин вызывал удалённый
  `internalAdapter.findAccountByProviderId`; заменён на `findAccountByKey`.
- `SteamButton` на лендинге стал `PlayButton` — ссылкой на `/login`.
- 2026-10-23: Telegram Login Widget (§6.3, свой плагин с проверкой HMAC и `POST /telegram/callback`)
  заменён на OIDC-вход Telegram через тот же `genericOAuth`, что Pocket ID и Яндекс: discovery
  `https://oauth.telegram.org/.well-known/openid-configuration`, scope `openid profile`, PKCE,
  обязательная проверка ID-токена по JWKS. Userinfo-эндпоинта у Telegram нет — профиль
  (`sub`, `name`, `preferred_username`, `picture`) читается из ID-токена; почта по-прежнему
  синтетическая `tg_<sub>@telegram.invalid`, автосклейки нет. Переменные `TELEGRAM_BOT_TOKEN`/
  `TELEGRAM_BOT_USERNAME` заменены на `TELEGRAM_CLIENT_ID`/`TELEGRAM_CLIENT_SECRET` (BotFather →
  Login Widget), callback — `/api/auth/callback/telegram`, в BotFather он должен быть в Allowed URLs.
  `auth.providers.telegram` стал `boolean`, сторонний скрипт виджета и `signInWithTelegram` удалены;
  вход и привязка идут через `signIn.social`/`linkSocial` как у Яндекса. Регулярка синтетической
  почты ослаблена до `tg_<любой sub>@` [моё решение].

Пометка **[моё решение]** — выбор, сделанный при проектировании, а не владельцем продукта; его можно оспорить. Всё без пометки — решено владельцем на брейншторме.

Прототип страницы входа: `docs/brand/prototypes/login-concepts.html` — пять концепций, выбрана **03 «Сборка куба»** (секция `#secC`, скрипт `// ---------- C: сборка куба ----------`). Правая панель прототипа ещё с паролем; по решению владельца пароля не будет (§4.2).

Связанные документы: основная спека `docs/superpowers/specs/2026-10-16-cloud-gaming-mvp-design.md` (её §3 п. 1 «вход через Steam OpenID» этот документ **заменяет**), спека лендинга `docs/superpowers/specs/2026-10-17-gamecrate-brand-and-landing-design.md` (кнопки «Войти через Steam» на лендинге меняются, §7.1).

## 1. Зачем

Сейчас на сайт входят только через Steam (игроки) и Pocket ID (админы), привязка аккаунтов отключена. Владелец хочет, чтобы человек **сначала заводил аккаунт на платформе** — через Яндекс, Google, Telegram или по почте — и потом **привязывал игровые аккаунты** (Steam сейчас, другие позже) к этому одному аккаунту. Один человек = один аккаунт независимо от того, какой кнопкой он вошёл.

Страница входа должна выглядеть как у хороших SaaS: слева живая интерактивная сцена, справа компактная панель входа. Пароля нет вообще: вход по почте — одноразовый код из письма.

## 2. Цели, не-цели, анти-цели

**Цели**

- Страница `/login` в концепции «Сборка куба»: один экран и для входа, и для регистрации. Способы: Яндекс, Google, Telegram, почта с одноразовым кодом.
- Steam перестаёт быть способом входа и становится **привязкой** внутри аккаунта. Библиотека, сессии и всё, что завязано на `steamId`, работают как раньше после привязки.
- Страница профиля `/profile` с разделом «Способы входа»: привязать/отвязать Яндекс, Google, Telegram, Pocket ID, Steam; добавить или сменить почту. Последний способ входа отвязать нельзя.
- Автоматическая склейка по подтверждённой почте: вход через Google/Яндекс/Pocket ID с почтой существующего аккаунта — это вход в тот же аккаунт, а не новый пользователь.
- Админ входит через Pocket ID как обычный пользователь; роль `admin` по-прежнему из группы Pocket ID; к его аккаунту привязываются Steam и остальные способы.
- Письма с кодом уходят через SMTP владельца.
- Новичок после входа видит библиотеку с заметной плашкой «Подключи Steam» и кнопкой привязки.

**Не-цели**

- Редизайн приложения (библиотека, шапка, админка) — владелец сделает отдельно. Здесь меняется минимум: плашка в библиотеке, ссылка на профиль в шапке.
- Пароли, «Забыл пароль», двухфакторка, passkeys.
- Другие игровые платформы (Epic, GOG, Xbox) — только Steam; но модель «аккаунт → привязки» готова к ним.
- Удаление аккаунта, смена имени и аватара, уведомления в Telegram (кнопка в прототипе 05 это обещала — не обещаем).
- Приглашения, капча, антифрод сложнее лимитов запросов.

**Анти-цели** (провал, даже если «работает»)

- **Кража аккаунта через почту**: склейка по почте только с адресами, которые подтвердил провайдер (Google, Яндекс, Pocket ID) или сам пользователь кодом. Telegram и Steam почту не дают — они **никогда** не склеиваются автоматически.
- Пользователь остаётся без способа входа (отвязал последнее).
- Чужой Steam: привязать можно только Steam, которым ты владеешь (OpenID-подтверждение), и который не привязан к другому живому аккаунту.
- Роль `admin` у того, кого убрали из группы Pocket ID, живёт дольше, чем до его следующего входа через Pocket ID (см. §6.6, принятый остаток риска).
- Секреты (токен бота, client secret, пароль SMTP) в логах, тестах, коммитах или ответах API.
- Код из письма в логах прода.
- Ломается то, что работает: Pocket ID-вход админа, библиотека и синхронизация по `steamId`, RPC-сессия по cookie, деплой.

## 3. Как это выглядит для людей

### 3.1 Новичок

1. На лендинге нажимает «Играть» → `/login`.
2. Слева кубики летают в беспорядке, справа панель. Нажимает «Войти через Google» → Google → возвращается уже вошедшим, попадает в `/library`.
3. В библиотеке пусто, большая плашка: «Подключи Steam, чтобы увидеть свою библиотеку» и кнопка «Привязать Steam». Нажимает → Steam OpenID (QR в приложении Steam или логин) → возвращается в `/library`, библиотека синхронизируется как сейчас при входе.

Вариант по почте: вводит адрес → «Получить код» → письмо с шестью цифрами → вводит код → вошёл (аккаунт создан, почта подтверждена). Никакой отдельной «регистрации» нет: неизвестный адрес просто становится новым аккаунтом.

### 3.2 Возвращение другим способом

Человек регистрировался по почте `ivan@gmail.com`, через месяц нажал «Войти через Google» с тем же адресом → попадает в **свой** аккаунт, Google теперь привязан (видно в профиле). То же для Яндекса и Pocket ID.

Если вошёл через Telegram, а раньше был аккаунт по почте — это **другой** аккаунт (Telegram почту не даёт). Он может в профиле добавить почту кодом — но если адрес уже занят другим аккаунтом, получит понятное сообщение: «Этот адрес уже привязан к другому аккаунту. Войди в него и привяжи Telegram там». Ручного слияния двух аккаунтов нет (не-цель).

### 3.3 Профиль → «Способы входа»

Список: Яндекс, Google, Telegram, Pocket ID, Steam, Почта. У каждого статус («привязан», «не привязан»), детали где есть (почта, имя Steam-профиля), кнопка «Привязать» / «Отвязать». Отвязка последнего способа недоступна с подсказкой почему. Steam отвязывается тоже (библиотека при этом остаётся в базе, но перестаёт обновляться до новой привязки — [моё решение]: не чистим, при повторной привязке того же Steam она просто продолжит синхронизацию).

### 3.4 Админ

Входит через Pocket ID (кнопка на `/login` **не** показывается в общем ряду — [моё решение]: небольшая ссылка «Вход для команды» под панелью, чтобы не путать игроков; админ попадает в `/admin`, как сейчас). В профиле привязывает Steam и играет как все. Войти может и через Google с той же почтой — склейка по почте работает и для него.

### 3.5 Существующие пользователи Steam

Сейчас в проде есть пользователи, созданные Steam-входом: синтетическая почта `steam_<id>@…`, единственная привязка — Steam. Владелец подтвердил (2026-10-22): это только он сам, данные не жалко. Поэтому **автоматического переноса старых записей нет**. Перед первым деплоем этой работы владелец один раз удаляет старых Steam-пользователей в базе прода (запись в `user` каскадом уносит `account`, `session`, `user_games` и остальные таблицы с `user_id`); шаг описан в `deploy/README.md` вместе с готовым SQL `DELETE FROM "user" WHERE email LIKE 'steam\_%@%' AND id NOT IN (SELECT user_id FROM account WHERE provider_id <> 'steam-openid')`. После этого привязка Steam к новому аккаунту проходит чисто. Если такой пользователь всё же останется, привязка его Steam даст штатную ошибку плагина «Steam уже привязан к другому аккаунту» — данные никуда не переезжают.

## 4. Страница входа `/login`

### 4.1 Компоновка

Два столбца на десктопе (сцена слева ~55 %, панель справа), на телефоне — панель сверху, сцена под ней укорочена до ~240px (кубики видны, подписи шагов скрыты). Фон и палитра — брендовые (`#05060f`, градиент `#3cc2ff → #3a6cff → #5b2fff`), шрифты Inter + JetBrains Mono из `src/fonts.ts`. Логотип (знак + слово) в левом верхнем углу сцены, ссылка на `/`.

Если пользователь уже вошёл — `/login` сразу перенаправляет на `next` или `/library`.

### 4.2 Правая панель

Заголовок «Войти в GameCrate». Три кнопки одной высоты: «Войти через Яндекс» (красная, буква Я), «Войти через Google» (белая, G), «Войти через Telegram» (голубая, самолётик). Разделитель «или по почте». Поле почты и кнопка «Получить код». Под панелью мелко: «Входя, ты создаёшь аккаунт GameCrate, если его ещё нет» и ссылка «Вход для команды» (Pocket ID, §3.4).

Шаг с кодом: после отправки поле почты сворачивается в строку «Код отправлен на ivan@…  Изменить», появляется поле на 6 цифр (автофокус, вставка из буфера, автоподтверждение по 6-й цифре), кнопка «Войти», ссылка «Отправить ещё раз» (доступна через 30 с, таймер виден). Ошибки прямо под полем: «Неверный код», «Код устарел, отправь новый», «Слишком много попыток, запроси новый код».

Кнопки провайдеров, которые не настроены на сервере (нет ключей в окружении), **не показываются** — панель узнаёт список у сервера (§6.4). Пока список не пришёл — скелетон кнопок, не пустота.

Ошибки возврата от провайдеров (`/login?error=…`) показываются тостом и строкой над панелью, человеческим языком: «Google не подтвердил вход», «Этот Steam уже привязан к другому аккаунту», «Этот аккаунт уже привязан к другому пользователю GameCrate» и т. д. Коды → тексты в одном словаре на фронте.

### 4.3 Левая сцена — «Сборка куба» (по прототипу)

Canvas с 27 изометрическими кубиками (3×3×3, ребро ~34px на десктопе) в цветах палитры. Состояние сцены — «уровень сборки» 0..2:

- уровень 0 (ничего не введено): 9 кубиков нижнего слоя на месте, остальные медленно дрейфуют в беспорядке вокруг (синус-дрейф ±14px);
- уровень 1 (введена почта, похожа на адрес): 18 кубиков на месте;
- уровень 2 (код введён целиком / нажата кнопка провайдера): все 27 собраны;
- «зажигание»: при успешной отправке (нажали «Войти» с кодом или кнопку провайдера) куб пульсирует и вокруг расходится голубое свечение ~2,5 с, пока идёт редирект.

Кубики едут к месту с лёгкой инерцией (0,06 за кадр). Наведение на кнопку провайдера перекрашивает все кубики в цвет сервиса (Яндекс `#fc3f1d`, Google `#4285f4`, Telegram `#29a9eb`); уход — обратно в палитру. Справа сверху подписи шагов в моно-шрифте: «учётка · код · облако» с зелёной точкой у пройденных (в прототипе «пароль» — заменить на «код»). Подпись внизу: `ASSEMBLING` и фраза по уровню: «Твоё облако собирается» / «Почти готово…» / «Облако собрано. Поехали!».

Поведение на мышь только локальное (цвет, уровень), никакого параллакса — владельца укачивает (см. спеку лендинга). `prefers-reduced-motion`: кубики стоят собранными на уровне по состоянию формы без дрейфа и инерции, свечение без пульсации. Цикл рисования — через существующий `useCanvasLoop` (рисует только когда вкладка видна).

### 4.4 Поведение после входа

Как и сейчас при выходе: RPC-сокет привязан к cookie апгрейда, поэтому после успешного входа делаем полную навигацию (`window.location.assign(next)`), а не клиентский переход. `next` берётся из `?next=` (только относительные пути с ведущим `/`, иначе `/library`); провайдерам отдаётся как `callbackURL`.

## 5. Профиль `/profile`

Страница для вошедшего под `AppHeader` (как `/library`). Переход — клик по аватару/имени в шапке [моё решение]. Разделы:

1. **Аккаунт**: аватар, имя, почта (или «Почта не добавлена» для аккаунтов из Telegram, у которых адрес синтетический). Кнопка «Добавить почту» / «Сменить почту»: поле адреса → код на **новый** адрес → подтверждение → адрес становится почтой аккаунта и подтверждён. Старую почту кодом не подтверждаем [моё решение] — у нас нет паролей, вход уже доказан сессией.
2. **Способы входа**: строки Яндекс, Google, Telegram, Pocket ID, Steam. Для привязанных — «Отвязать», для остальных — «Привязать» (запускает тот же поток, что вход, но в режиме привязки; возврат — на `/profile`). Steam-строка показывает имя и аватар Steam-профиля, если есть. Непривязываемые на этом сервере (нет ключей) — не показываются.
3. **Выход** и, для админа, ссылка в админку (уже есть в шапке).

Правило «последний способ»: отвязать можно, если после этого у пользователя остаётся хотя бы один способ **войти**: любая привязка **кроме Steam** (Steam — не вход) или подтверждённая настоящая почта. То есть: у человека Google + Steam → Google отвязать нельзя; у человека почта + Google + Steam → Google отвязать можно. Сервер проверяет это сам, фронт лишь дизейблит кнопку с подсказкой.

Отвязка Pocket ID сбрасывает роль в `player` (§6.6).

## 6. Серверная часть

Стек тот же: Better Auth 1.7.10 на Effect-сервере `apps/api`, Drizzle + PostgreSQL, Effect RPC. Всё ниже — расширение `apps/api/src/auth/auth.ts` и соседей, плюс конфиг и деплой.

### 6.1 Провайдеры

| Способ | Как | Почта | Автосклейка по почте | Вход | Привязка |
|---|---|---|---|---|---|
| Почта + код | плагин `emailOTP` (`/email-otp/send-verification-otp`, `/sign-in/email-otp`) | своя, подтверждена кодом | да (это и есть идентичность) | да | «Добавить/сменить почту» через `change-email` того же плагина |
| Google | встроенный провайдер Better Auth | подтверждённая | да | да | `/link-social` |
| Яндекс | `genericOAuth`, providerId `yandex`: authorize `https://oauth.yandex.ru/authorize`, token `https://oauth.yandex.ru/token`, userinfo `https://login.yandex.ru/info?format=json`, scopes `login:email login:info login:avatar`; `getUserInfo` → `id`, `default_email`, имя из `display_name`/`real_name`/`login`, аватар `https://avatars.yandex.net/get-yapic/<default_avatar_id>/islands-200` если `!is_avatar_empty`, `emailVerified: true` | подтверждённая (почта Яндекса) | да | да | `/link-social` |
| Pocket ID | `genericOAuth` как сейчас; `mapProfileToUser` дополнительно отдаёт `emailVerified` из claim `email_verified` | подтверждённая | да | да (ссылка «для команды») | `/link-social` |
| Telegram | **свой плагин** `apps/api/src/auth/telegram.ts` (§6.3) | нет (синтетическая `tg_<id>@telegram.invalid`) | **нет** | да | да |
| Steam | `better-auth-steam` как сейчас, но **только** `/steam/link` + `/steam/callback`; `/steam/login` закрыт хуком `before` → 404 [моё решение] | синтетическая (только у старых пользователей) | **нет** | **нет** | да |

Все провайдеры **необязательны в конфиге**: нет `GOOGLE_CLIENT_ID` — провайдер не регистрируется и не показывается на фронте. Pocket ID и Steam обязательны как сейчас (на них держатся админка и библиотека).

### 6.2 Привязка и склейка (настройки Better Auth)

Все опции ниже существуют в установленной версии — проверено по типам и коду: `node_modules/.bun/@better-auth+core@1.7.10*/node_modules/@better-auth/core/dist/types/init-options.d.mts` (`accountLinking`: `enabled`, `disableImplicitLinking`, `requireLocalEmailVerified`, `trustedProviders`, `allowDifferentEmails`, `allowUnlinkingAll`), `better-auth/dist/api/routes/account.mjs` (`/link-social`, `/unlink-account`, `/list-accounts`, проверка «последний account»), `better-auth/dist/oauth2/link-account.mjs` (правило неявной склейки: доверенный провайдер **или** `emailVerified` из профиля, плюс `requireLocalEmailVerified`).

- `account.accountLinking.enabled: true`.
- `trustedProviders: ["google", "yandex", "pocket-id"]` — неявная склейка по почте при входе (поверх собственного `emailVerified` из профиля). `requireLocalEmailVerified` остаётся по умолчанию `true`: склеиваемся только с пользователем, чья почта подтверждена — у нас это все, кроме синтетических.
- `allowDifferentEmails: true` — явная привязка из профиля не требует совпадения почты (нужно и плагину Steam). Привязка аккаунта провайдера, который уже привязан к **другому** пользователю, отклоняется самим Better Auth — на фронте текст «уже привязан к другому аккаунту GameCrate».
- `allowUnlinkingAll: true` + собственный хук `before` на `/unlink-account`, реализующий правило §5 (у Better Auth правило «последний account-ряд», а у почтового пользователя account-рядов нет вовсе — `emailOTP` их не создаёт).
- Steam-вход: хук `before` на `/steam/login` → 404. Поток `link` плагина остаётся.
- Старые Steam-пользователи (§3.5): никакой логики переноса — только разовая ручная чистка перед деплоем.

### 6.3 Плагин Telegram

Telegram Login Widget не даёт OAuth: виджет отдаёт подписанный набор полей `id, first_name, last_name, username, photo_url, auth_date, hash`. Плагин:

- `POST /telegram/callback` (тело — эти поля + `callbackURL`, опционально режим `link`): проверяет подпись — `data_check_string` = отсортированные `key=value` через `\n` без `hash`, ключ = `SHA256(bot_token)`, `HMAC-SHA256` hex должен совпасть с `hash`; `auth_date` не старше 5 минут; иначе 401. Дальше: есть сессия и режим `link` → создать `account {providerId: "telegram", accountId: id}` (если id уже у другого пользователя — ошибка «уже привязан»); нет сессии → найти пользователя по `account` и создать сессию, либо создать нового (`name` из `first_name [last_name]` или `@username`, `image` = `photo_url`, почта синтетическая `tg_<id>@telegram.invalid`, `emailVerified: false`) и создать сессию. Домен `.invalid` зарезервирован RFC 2606 и не может совпасть с настоящим адресом; «подтверждённая почта» везде в документе означает флаг `user.emailVerified` в нашей базе (провайдеры лишь задают его при создании/склейке). Ответ — JSON `{ redirect: callbackURL }`, cookie сессии ставится как у остальных входов.
- Фронт: кнопка «Войти через Telegram» своя (в стиле панели); по клику грузится официальный `https://telegram.org/js/telegram-widget.js` (один раз, лениво) и вызывается `window.Telegram.Login.auth({ bot_id, request_access: false }, data => …)`, данные уходят в `POST /api/auth/telegram/callback`. Это единственный сторонний скрипт в приложении, грузится только по клику [моё решение]. Имя/ID бота фронт получает из `auth.providers` (§6.4).
- Тесты подписи — на фикстуре с тестовым токеном (никогда не настоящим).

### 6.4 Что фронт узнаёт у сервера

Новая **публичная** RPC-группа (без `AuthMiddleware`) `PublicAuthRpcs` с `auth.providers` → `{ google: boolean; yandex: boolean; telegram: { botId: string; botUsername: string } | null; pocketId: boolean }`. Секреты сюда не попадают (bot id и username — публичные). [моё решение] Это отдельный `RpcGroup.make(...)` рядом с `AuthRpcs` в `packages/rpc/src/auth.ts`, без мидлваров, добавленный в `AppRpcs`; ответ только читает конфиг, поэтому дополнительной защиты сверх существующей проверки Origin на `/rpc` не нужно. Фронт запрашивает его атомом как `meAtom`, до входа.

`CurrentUserShape` (`auth.me`) расширяется: `email: string | null` (null для синтетической), `emailVerified: boolean`. `steamId` остаётся. Список привязок профиль берёт штатным `authClient.listAccounts()`; Steam-имя/аватар — из `auth.me` (новые поля `steamName`, `steamAvatar` [моё решение] — плагин их не хранит, берём из существующего `SteamApi.getPlayerSummary`-подобного вызова при синхронизации или привязке; если это дорого, строитель может показывать только SteamID).

### 6.5 Почта и коды

- Плагин `emailOTP`: 6 цифр, срок 10 минут, 3 попытки на код, хранение `hashed`, `resendStrategy: "rotate"`, `rateLimit` плагина: не чаще 1 письма в 30 с на адрес и 10 в час на адрес [моё решение]. Общий `rateLimit` Better Auth включён в проде по умолчанию — оставить.
- Смена/добавление почты (§5) — через `changeEmail: { enabled: true, verifyCurrentEmail: false }` **этого же плагина** (`/email-otp/request-email-change` → код на новый адрес → `/email-otp/change-email`); core-поток `user.changeEmail` остаётся выключенным, чтобы не было двух способов [моё решение].
- Отправка: сервис `Mailer` (`apps/api/src/mail/Mailer.ts`, `Context.Service`, как `SteamApi`) с методом `send({ to, subject, text, html }) => Effect<void, MailError>`. Слой `BetterAuth` получает его как зависимость и в колбэке `sendVerificationOTP` запускает `send` через рантайм слоя (`Effect.runtime` → `Runtime.runPromise`) и **ждёт** результата: ошибка SMTP → колбэк бросает → Better Auth отвечает ошибкой → фронт показывает «Не удалось отправить письмо, попробуй позже». `log://` пишет через `Effect.logInfo` [моё решение]. Реализация — `nodemailer` поверх SMTP [моё решение, точная версия закреплена, работает в Bun]. Конфиг: `SMTP_URL` (Redacted, вида `smtps://user:pass@host:465` или `smtp://…:587` со STARTTLS) и `MAIL_FROM` (например `GameCrate <no-reply@brofrong.ru>`). Для разработки `SMTP_URL=log://` — письмо целиком пишется в лог сервера; в проде это значение запрещено (`PUBLIC_URL` не localhost → ошибка конфигурации при старте) [моё решение].
- Письмо «Код для входа в GameCrate»: код крупно, «действует 10 минут», «если это не ты — просто проигнорируй письмо». Текстовая и HTML-версии, без картинок с CDN. Второй шаблон — «Подтверди новую почту» для смены адреса.
- Код и адрес получателя в логах прода не пишутся; пишется факт отправки и ошибка SMTP без тела.

### 6.6 Роли

- Как сейчас: роль пересчитывается из группы при **каждом входе через Pocket ID** (`session.create.before`).
- Новое: при **привязке** Pocket ID из профиля роль тоже пересчитывается (в хуке `after` на callback привязки) — чтобы админу не нужно было перелогиниваться.
- Новое: при **отвязке** Pocket ID роль становится `player`.
- Остаток риска, принятый владельцем: админ, исключённый из группы, сохраняет роль до следующего входа через Pocket ID или отвязки. Для нашей команды это приемлемо; смягчение — отвязать/удалить вручную.

Callback-адреса, которые владелец укажет у провайдеров (`PUBLIC_URL` = `https://game.brofrong.ru`):
