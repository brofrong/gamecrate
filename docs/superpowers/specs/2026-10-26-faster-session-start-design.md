# GameCrate — запуск игры быстрее — дизайн

Дата: 2026-10-26. Статус: дизайн, ждёт одобрения владельца.

## 1. Зачем

Владелец назвал долгое ожидание при запуске самой большой проблемой («Нет прогрес бара очень долго
ждать», backlog §«Прогресс виден с первой секунды»). Из двух путей — показывать этапы или сократить
само ожидание — владелец выбрал **«само ожидание короче»**. Этот дизайн только про сокращение;
показ этапов — отдельный следующий шаг (§7).

Что видит игрок сейчас:
- ~10 с экран «Запускаем игру…»;
- затем трансляцию пустого рабочего стола KDE (`StreamReady` приходит, как только поднялся
  Selkies);
- около двух минут ничего не происходит: `cg-launch` запускает `steam -silent -applaunch`, окно
  Steam скрыто;
- потом появляется игра.

## 2. Замер (2026-10-26, прод brofrong, main 1ec73c8)

Один запуск уже установленной Can of Wormholes. Игрок с профилем и входом в Steam. От нажатия
«Играть» до `Game started` — **142 с**:

| Отрезок | Время | Что происходит (по логам Steam, контейнера и агента) |
|---|---|---|
| Очередь, создание и старт контейнера | ~2 с | |
| Рабочий стол до `cg-launch` | ~8 с | |
| Старт steamwebhelper | **67 с** | pressure-vessel (`steamrt64/pv-runtime/…/_v2-entry-point`) при каждом старте делает жёсткие ссылки на рантайм (`steamrt3c_platform_*`, ~313 МБ мелких файлов) в `var/tmp-*`. На overlay жёсткая ссылка на файл из lower — это полный copy-up в upper, и overlay делает fsync каждого файла |
| Старт интерфейса | ~4 с | |
| `steamui_login`: `[ WaitingForNetwork ] Timed out waiting for network` | **20 с** | сеть есть, тест связи проходит. `client_networkmanager.txt`: «create NetworkManager client: success», но службы NetworkManager в контейнере нет, и Steam не получает состояние сети, пока не выйдет таймаут |
| Вход | ~1 с | |
| `WaitingForLibraryReady` | **28 с** | кэш `appcache/appinfo.vdf` в шаблоне клиента устарел (change number 40250274 → 40253228), и Steam при каждом запуске докачивает данные о ~2528 приложениях (~14,6 МБ) |
| Запуск игры | ~8 с | |

Отдельный стенд на brofrong (временный overlay-том того же вида, что создаёт агент, и только
copy-up рантайма):
- сейчас 33–39 с;
- шаблон клиента на NVMe вместо HDD RAID — без изменений: медленная запись копии, а не чтение;
- с опцией монтирования overlay **`volatile`** — ~1 с. Ядро brofrong — 6.12, опция есть с 5.10.

## 3. Цели, не-цели, анти-цели

Цели:
- **Запуск уже установленной игры ≤ 60 с** от нажатия «Играть» до `Game started` (цель из
  бэклога). Меряется медианой трёх запусков на brofrong: игрок с профилем и входом, слот свободен,
  установки нет.
- Попутно, тем же изменением (§4.1): быстрее стартует Steam в установщике — сейчас минута и больше
  на 0 % до начала скачивания.

Не-цели:
- Показ этапов и прогресса на экране ожидания (§7).
- Плавный процент скачивания при установке.
- Скорость самого скачивания игр.
- Время в очереди при занятом слоте.

Анти-цели — провал, даже если стало быстрее:
- Потеря профиля или сохранений игрока при штатной остановке, при сбое сохранения
  (`profile-unsaved`) или при перезапуске агента.
- Битая игра в общей библиотеке после установки.
- Обязанность владельца руками что-то регулярно делать, чтобы ускорение не деградировало. Сейчас
  пересборка шаблона требует простоя сервиса — стать регулярной она не должна.
- Ослабление изоляции контейнера: новые привилегии, доступ к хосту, root в контейнере.

## 4. Что меняется

Порядок — по убыванию выигрыша. После каждого пункта — повторный замер (§5).

### 4.1 `volatile` на одноразовых слоях

Добавить `volatile` в опции overlay-тома (`apps/agent/src/DockerClient.ts`, тело
`POST /volumes/create`, сейчас `lowerdir=…,upperdir=…,workdir=…`). Включать по слою:

| Слой | `volatile` | Почему |
|---|---|---|
| Сессия, `client` | да | одноразовый: профиль уходит архивом через `cg-profile-pack`, upper после сессии удаляется |
| Сессия, `apps` | да | там Proton-сохранения (`compatdata/*/pfx/…`) до упаковки профиля; при сбое хоста посреди сессии они и сейчас не сохраняются, профиль пишется только при остановке |
| Установщик, `client` | да | одноразовый, как у сессии |
| Установщик, `apps` | **нет** | upper `rename`-ом переносится в общую библиотеку. После сбоя хоста без fsync там могла бы оказаться битая игра |

Последствия, которые надо закрыть в этой же работе:
- **Повторное монтирование.** После монтирования с `volatile` ядро оставляет
  `<workdir>/work/incompat/volatile`. Пока этот каталог есть, повторно смонтировать тот же
  upper/work нельзя. Это ломает восстановление `profile-unsaved` из `deploy/README.md`:
  `docker start cg-session-<id>` монтирует тома заново.

  Решение (моё, не владельца): когда агент останавливает контейнер как `profile-unsaved`, тома
  размонтируются. Сразу после этого агент через помощника от root:
  1. делает `sync` файловой системы scratch (данные upper на диске, как было без `volatile`);
  2. удаляет `work/incompat` обоих слоёв.

  После этого восстановление по README работает как раньше, и сбой хоста после остановки ничего не
  теряет. Если агент не успел (упал между остановкой и уборкой метки), он делает то же при старте
  для остановленных контейнеров `cg.session` (их он и сейчас находит). README: одна фраза, что
  `docker start` при ошибке «volatile» лечится перезапуском агента.

  До того как строить на этом решение, проверить на brofrong:
  - что метка именно такая;
  - что тома при остановке контейнера действительно размонтируются;
  - что после удаления метки повторный старт работает.
- Уборка осиротевших слоёв уже удаляет каталоги от root целиком. Проверить, что метка
  `incompat/volatile` ей не мешает.

Если после `volatile` старт steamwebhelper всё ещё дольше ~10 с, то запасной вариант из бэклога —
держать распакованную среду pressure-vessel готовой в шаблоне клиента. Делать его только по
результату замера.

### 4.2 Свежий кэш данных о приложениях

Цель: в момент запуска `appcache/appinfo.vdf` в шаблоне клиента отстаёт не больше чем на сутки,
и `WaitingForLibraryReady` занимает ≤ 5 с.

Сначала замерить, без изменений в коде:
- пересобрать шаблон (`deploy/build-steam-client.sh`) и измерить `WaitingForLibraryReady` сразу;
- измерить ещё раз через ~сутки.

Если через сутки всё ещё ≤ 5 с, то хватит обновлять кэш раз в сутки. Если нет, обновлять чаще или
искать другой способ.

Как поддерживать свежесть — решает исполнитель, в рамках ограничений:
- lower нельзя менять, пока его монтирует хоть один контейнер;
- нельзя требовать простоя сервиса или ручного запуска владельцем (анти-цель);
- шаблон собирается без входа в аккаунт, и в нём не должно оказаться ничего от игроков.

Направление на мой взгляд, не обязательное:
- версии шаблона рядом друг с другом (`steam-client/<версия>`);
- агент или фоновая задача собирает новую версию в простое слота;
- новые сессии берут свежую версию, старая удаляется, когда её больше никто не монтирует.

Это же снимает «сессии начали подолгу входить — клиент Steam обновился» из README.

Хранить кэш в профиле игрока — **нет**: +15 МБ на каждое сохранение, у каждого игрока свой
устаревший кэш.

### 4.3 Ожидание сети 20 с

Причина пока не доказана. Гипотеза — клиент NetworkManager в Steam подключается к D-Bus, но
службы `org.freedesktop.NetworkManager` нет, состояние сети неизвестно, и Steam ждёт таймаута.

Основания гипотезы:
- `client_networkmanager.txt`: «create NetworkManager client: success» и дальше ничего;
- `steamui_login`: ровно 20 с между `WaitingForNetwork` и «Timed out waiting for network», затем
  сразу успешный вход.

Цель ≤ 60 с достижима и без этого пункта: 142 − ~60 (§4.1) − ~25 (§4.2) ≈ 57 с. Поэтому
исследование можно вести параллельно с §4.1–4.2 и не блокировать ими.

Ограничить исследование ~полудня работы. Итог:
- либо ожидание убрано, например заглушка NetworkManager в контейнере отвечает Steam «сеть есть» без новых
  привилегий, или Steam запускается так, что сеть не ждёт;
- либо в этом документе записано, почему не получилось, и пункт уходит в бэклог.

Способ — решает исполнитель. Ограничение: без привилегий и без доступа к D-Bus хоста.

## 5. Как меряем

- Скрипт замера, который можно запускать повторно. Время — `date +%s%N` и арифметика shell/awk:
  `bc` на brofrong нет.
- Точки: нажатие (`sessions.created_at` или вызов `startSession`), `Session container started`,
  `cg-launch`, отрезки из логов Steam (`steamui_login`, `webhelper`), `Game started` агента.
- Каждый замер — три запуска, медиана.
- Результаты до и после каждого пункта §4 дописать в этот документ, раздел «Результаты».
- Замер не трогает чужие контейнеры, тома и образы. Временные файлы убираются. Временные
  контейнеры запускаются только с явным `--entrypoint`.

## 6. Ограничения

- Хост brofrong: без sudo, без изменения настроек хоста, без перезагрузки, без
  `docker * prune`. Чужие контейнеры, тома и сети не трогать.
- Деплой — как в `deploy/README.md`, только когда нет живых `cg.session`/`cg.install`.
- Изменения шаблона клиента и образа сессии — только своим кодом, по правилам
  `build-steam-client.sh`. Сам скрипт отказывается работать под живыми сессиями.
- Токен и имя аккаунта Steam не должны попадать в логи замеров.

## 7. Дальше (не в этой работе)

Показ этапов на экране ожидания — отдельный шаг после этой работы, с макетом для владельца.
Сейчас игрок ~130 с смотрит на пустой рабочий стол. Набросок: этапы «Готовим компьютер»,
«Запускаем Steam», «Входим», «Запускаем игру» по новому отчёту агента. Решить, показывать ли
этапы поверх трансляции или вместо неё: Steam может показать окно, которое требует действия
игрока.

## Результаты

### Проверка `volatile` (Task 1, 2026-10-27, brofrong, ядро 6.12.111)

Стенд: свой overlay-том `local` с `…,volatile` и временный контейнер образа сессии с явным
`--entrypoint`; том подключён как у агента — `--mount type=volume,…,volume-nocopy`
(`VolumeOptions.NoCopy`). Стенд убран.

1. После первого монтирования появляется `<workdir>/work/incompat/volatile` (root, права 000).
   Внутри контейнера `/proc/mounts` показывает опцию `volatile`.
2. После выхода контейнера тома в `/proc/mounts` нет — остановка размонтирует том.
3. Повторный `docker start` с меткой падает:
   `failed to mount local volume: mount overlay:…, data: lowerdir=…,upperdir=…,workdir=…,volatile: invalid argument`.
   После `rm -rf <workdir>/work/incompat` помощником от root тот же контейнер стартует.

Что ещё выяснилось:
- Без `nocopy` Docker монтирует пустой именованный том ещё при `docker create`, чтобы скопировать
  в него содержимое образа. Метка появляется уже тогда, и первый же `docker start` падает с той же
  ошибкой. Агент подключает тома с `NoCopy: true`, и том слоя монтирует только один контейнер
  (`RestartPolicy: no`), так что это его не касается. Но любой новый код, который подключит том
  слоя второй раз (помощник, повторный старт), должен сначала снять метку.
- Данные из upper после остановки на месте (`b` в upper).
