# Требования игр к железу и классы воркеров

Дата: 2026-10-29. Решения владельца — в чате (вопросы с вариантами), дизайн утверждён целиком.

## Зачем

Сейчас планировщик (`apps/orchestrator/src/Scheduler.ts`) ставит любую игру в первый свободный
слот любого воркера: у игр нет требований к железу, а снимок железа воркера (`workers.hardware`:
CPU, RAM, GPU и видеопамять) нигде, кроме админки, не используется.

Повод — пробный запуск Bloodborne (bbport) 2026-10-28 на brofrong (GTX 1650 Super, 4 GB). В меню
игра шла 48 FPS, но после загрузки сохранения упала внутри драйвера NVIDIA: кэш текстур вырос до
3,4 GB на карте с 4 GB. Когда воркеров станет больше и они будут разными, тяжёлая игра не должна
попадать на слабую карту, а падения такого рода должны быть видны в админке без ssh.

Эта спека — первая из двух. Вторая («свои сборки»: bbport и другие порты вне Steam) будет
опираться на неё.

## Цели

1. **Допуск игры на воркер.** Игра запускается только на воркере, чьё железо покрывает её
   требования: видеопамять, оперативная память, потоки CPU.
2. **Классы воркеров.** Админ ведёт список классов («Стандарт», «Быстрое», …), упорядоченный по
   силе, и назначает класс каждому воркеру. Классы — основа будущих тарифов.
3. **Задел под тарифы.** Тарифа у пользователя пока нет; выбор воркера уже идёт через функцию
   «какие классы доступны пользователю», которая сейчас возвращает все классы.
4. **Замеры.** По каждой сессии сохраняются пиковые ресурсы игры, модель GPU и то, чем
   закончилась игра (сама, падение, остановка). Админка показывает их по игре в разрезе моделей
   GPU и предлагает требования, которые админ принимает или правит.
5. **Игрок видит «недоступна»,** если сейчас нет ни одного подходящего ему воркера.

## Не цели (сейчас)

- Тарифы целиком: таблица тарифов, поле у пользователя, оплата, часы — отдельная задача; здесь
  только функция-задел (§2.4).
- Плотная упаковка: несколько игр на одной карте по ресурсам вместо фиксированных слотов.
- Разные настройки игры под разное железо (например, bbport 720p на 4 GB и 1080p на 8+ GB).
- Свои сборки (bbport) — следующая спека.
- Требования из системных требований Steam (свободный текст, неточный; для своих сборок его нет).
- Требование к модели/поколению GPU отдельно от видеопамяти.

## 1. Данные

### 1.1 Классы воркеров

Новая таблица `worker_classes`:

| поле | тип | смысл |
|---|---|---|
| `id` | uuid | |
| `name` | text, уникальное | «Стандарт», «Быстрое» |
| `rank` | integer, уникальное | порядок по силе: больше — сильнее |
| `created_at` | timestamptz | |

`workers.class_id` — nullable FK на `worker_classes.id` (`on delete restrict`: класс с воркерами
удалить нельзя, сначала переназначить).

**Воркер без класса сессий не берёт** (как `draining` для сессий). Установки (`gamestore`) класс
не ограничивает.

**Миграция:** создаёт класс «Стандарт» (`rank = 1`) и назначает его всем существующим воркерам.
Иначе brofrong после деплоя перестал бы брать сессии. Новые воркеры, подключившиеся после
миграции, приходят без класса — админ назначает.

### 1.2 Требования игры

Новая таблица `game_requirements` (одна строка на игру; нет строки — «данных нет», §2.3):

| поле | тип | смысл |
|---|---|---|
| `app_id` | integer PK, FK `games.app_id` | |
| `min_vram_bytes` | bigint | минимум видеопамяти на слот |
| `min_ram_bytes` | bigint | минимум оперативной памяти на слот |
| `min_cpu_threads` | integer | минимум потоков CPU на слот |
| `updated_by` | text, FK `user.id` | кто задал |
| `updated_at` | timestamptz | |

Все три минимума обязательны; «не важно» — ноль.

### 1.3 Замеры сессии

Новая таблица `session_metrics` (одна строка на сессию, пишет оркестратор по отчётам агента, §4):

| поле | тип | смысл |
|---|---|---|
| `session_id` | text PK, FK `sessions.id` | |
| `app_id` | integer | копия для выборок по игре |
| `worker_id` | text | |
| `gpu_name` | text | модель GPU воркера на момент сессии |
| `worker_class_id` | uuid, nullable | класс воркера на момент сессии |
| `slots` | integer | `SLOTS` воркера на момент сессии |
| `game_seconds` | integer | сколько шла игра (процесс игры жив) |
| `peak_vram_bytes` | bigint, nullable | максимум за сессию |
| `peak_ram_bytes` | bigint, nullable | максимум за сессию |
| `cpu_cores_p95` | real, nullable | p95 по замерам, в ядрах |
| `gpu_util_p95` | real, nullable | p95 загрузки GPU, % |
| `vram_source` | text | `process` или `gpu_total` (§4.1) |
| `game_end` | text, nullable | `quit` / `crash` / `error` / `stopped` / `unknown` (§4.2) |
| `updated_at` | timestamptz | |

`null` в ресурсах — замер не удался.

## 2. Выбор воркера

### 2.1 Подходит ли воркер

Воркер подходит игре для пользователя, если одновременно:

- агент подключён и воркер не на обслуживании (`draining = false`) — как сейчас;
- у воркера есть класс, и этот класс входит в `allowedClasses(user)` (§2.4);
- железо **на слот** покрывает требования игры: `gpus[0].memoryBytes / slots ≥ min_vram_bytes`,
  `memoryBytes / slots ≥ min_ram_bytes`, `cpuThreads / slots ≥ min_cpu_threads`
  (`hardware` из `workers`, `slots` — `SLOTS` агента). На brofrong `SLOTS = 1`, то есть всё железо;
- есть свободный слот (кроме проверки «недоступна», §3).

Воркер без `hardware` (старый агент) не подходит играм с ненулевыми требованиями.

### 2.2 Порядок

Среди подходящих — сначала воркеры самого сильного класса (наибольший `rank`), внутри класса — по
`id`, как сейчас. Слот — наименьший свободный, как сейчас.

### 2.3 Игра без данных

Нет строки в `game_requirements` — игра идёт **только на воркеры самого сильного класса из
доступных пользователю**: наибольший `rank` среди `allowedClasses(user)`, у которого есть хотя бы
один воркер не на обслуживании. Заняты — сессия ждёт в очереди, на слабые классы не уходит.

Следствие: сразу после деплоя данных нет ни у одной игры, и все они идут на самый сильный класс.
Пока воркер один (brofrong), поведение не меняется.

### 2.4 Задел под тарифы

`allowedClasses(userId): Effect<ReadonlyArray<WorkerClass>>` — в одном месте (пакет, который
видят и оркестратор, и api). Сейчас возвращает все классы. Когда появятся тарифы, он будет
возвращать классы тарифа пользователя; планировщик и сайт менять не придётся.

### 2.5 Очередь без затора

Сейчас `placeOne` берёт только самую старую `queued`-сессию установленной игры. С требованиями
она может ждать занятый мощный воркер, и тогда очередь встанет целиком. Новое правило: планировщик
перебирает `queued`-сессии от старых к новым (не больше 50 за проход) и размещает первую, для
которой есть подходящий свободный воркер. Каждая сессия — в своей транзакции под
`FOR UPDATE SKIP LOCKED`, как сейчас. Старшая сессия, которой подойдёт освободившийся воркер,
получит его первой — порядок перебора от старых к новым.

Ветка «сессия неустановленной игры уходит в установку» не меняется.

## 3. Сайт

Игра **недоступна** пользователю, если среди воркеров, которые подключены или были на связи за
последние 10 минут (чтобы перезапуск агента при деплое не мигал пометкой), не на обслуживании и с
классом из `allowedClasses(user)`, нет ни одного, кто подходит ей по железу (§2.1 без проверки
свободного слота; для игры без данных — §2.3).

- Библиотека `/app` и страница игры получают у игры флаг `available` (api считает его одним
  запросом на список: воркеры и классы читаются один раз, требования — по `app_id` списка).
- Недоступная игра: плитка остаётся в каталоге, на странице игры кнопка запуска неактивна и
  подпись «Сейчас нет подходящего сервера».
- api отказывает в создании сессии недоступной игры той же причиной.
- «Все подходящие заняты» — не «недоступна»: запуск разрешён, сессия ждёт в очереди.
- Сессия, которая уже стоит в очереди, а игра стала недоступной (воркер ушёл), остаётся в очереди
  до существующих таймаутов.

## 4. Замеры

### 4.1 Ресурсы

Агент, пока процесс игры жив, раз в 10 с снимает показатели контейнера сессии:

- **RAM и CPU** — статистика Docker API контейнера (`/containers/{id}/stats?stream=false`):
  память без страничного кэша, CPU — дельта в ядрах.
- **Загрузка GPU** — `utilization.gpu` из `nvidia-smi` (на карту целиком; при `SLOTS = 1` это
  загрузка сессии).
- **VRAM.** Агент работает в своём контейнере без PID-пространства хоста. Первый вариант
  (`vram_source = process`): host PID процессов контейнера из Docker API (`/containers/{id}/top`)
  сопоставляются с процессами в `nvidia-smi --query-compute-apps=pid,used_memory` (сюда попадают
  процессы `C+G`, как bb-probe). Если сопоставить нельзя (NVML в контейнере агента не отдаёт
  PID хоста или процесс игры чисто графический), берётся видеопамять, занятая на карте целиком,
  минус то, что было занято до запуска игры (`vram_source = gpu_total`); при `SLOTS = 1` это
  точно. Какой вариант работает — первая задача плана (проверить на brofrong).

Агент держит максимумы и выборку для p95 в памяти и раз в 60 с, а также при конце игры шлёт
оркестратору сообщение `SessionMetrics` (накопленные значения целиком; оркестратор пишет строку
`session_metrics` через upsert). Перезапуск агента теряет только последнюю минуту.

### 4.2 Чем закончилась игра

`game_end`:

- `stopped` — сессию остановили (игрок, сайт, админ, таймаут бездействия) до того, как игра
  закрылась сама;
- `quit` — процесс игры завершился сам с кодом 0;
- `crash` — процесс игры убит сигналом (SIGSEGV, SIGABRT и т.п.) или контейнер неожиданно
  остановился (`failReasons.containerGone`);
- `error` — процесс игры завершился сам с ненулевым кодом;
- `unknown` — игра закрылась сама, но код выхода узнать не удалось.

Код выхода сейчас не известен: агент только видит, что процесс игры пропал (`pgrep`). Нужна
обёртка `cg-game-exit`: запускает команду игры и пишет её статус (код или сигнал) в файл
`/tmp/cg-game-exit` контейнера; агент читает его, увидев конец игры.

- **Steam-игры:** обёртку можно поставить только через параметры запуска игры
  (`LaunchOptions` в `localconfig.vdf`: `cg-game-exit %command%`). Её пишет агент в
  `localconfig.vdf` контейнера перед стартом Steam и убирает перед сохранением профиля, чтобы она
  не уехала в профиль пользователя. Если Steam перезаписывает файл и это не держится — для
  Steam-игр остаётся `unknown`, кроме `stopped` и `containerGone`. Проверка — задача плана.
- **Proton:** часть падений Windows-игр Wine перехватывает сам, и процесс выходит «нормально» —
  такие падения будут `quit`/`error`. Это известное ограничение.
- **Свои сборки** (следующая спека) запускаются нашей командой, обёртка для них работает точно.

`GameState` агента (`running: false`) получает необязательное поле `end` с этим значением.

## 5. Админка

### 5.1 Классы

На вкладке «Воркеры» — блок «Классы»: список по силе (сильнейший сверху), добавить, переименовать,
поднять/опустить, удалить (если у класса нет воркеров). В карточке воркера — выбор класса; воркер
без класса помечен «Без класса — сессий не берёт».

### 5.2 Игра: требования и замеры

На странице игры в админке (`/admin` → «Игры» → игра):

- **Требования:** три поля (VRAM GB, RAM GB, потоки CPU) и «Сохранить»; пусто — «нет данных,
  запускается только на самом сильном классе».
- **Замеры по моделям GPU:** таблица — модель GPU, класс, сессий (с игрой дольше 5 минут), p95
  пиковой VRAM, p95 пиковой RAM, p95 CPU в потоках, p95 загрузки GPU, доля `crash`, доля
  `error`/`unknown`. Источник VRAM (`process`/`gpu_total`) — подсказкой.
- **Предложение:** по всем сессиям игры дольше 5 минут, если их не меньше 3: p95 пиковых значений
  плюс 20% запаса, VRAM округляется вверх до 0,5 GB, RAM — до 1 GB, потоки CPU — до целого.
  Кнопка «Принять» заполняет поля требований (сохранять — тем же «Сохранить»).
- **Подсказка о падениях:** если на какой-то модели GPU не меньше 3 сессий и `crash` в 30% и
  больше — строка «На <GPU> игра падает в N% сессий — поднять минимум VRAM выше <VRAM этой
  карты на слот>?» с кнопкой, подставляющей это значение (+0,5 GB) в поле.

Пороги (5 минут, 3 сессии, 20%, 30%) — константы в коде.

## 6. Проверки

- Планировщик: воркер без класса, класс вне `allowedClasses`, нехватка VRAM/RAM/CPU на слот,
  `SLOTS > 1` делит железо, игра без данных идёт только на сильнейший класс и ждёт его,
  порядок по классам, старая неподходящая сессия не блокирует новую.
- Миграция: существующие воркеры получают «Стандарт».
- `available` в библиотеке и на странице игры, отказ api при создании сессии.
- Агент: `SessionMetrics` (максимумы, p95, upsert), `game_end` для всех веток, обёртка
  `cg-game-exit` (код, сигнал).
- Админка: классы (CRUD, порядок, удаление занятого класса запрещено), требования, таблица
  замеров, предложение и подсказка о падениях.
- Ручная проверка на brofrong: какой источник VRAM работает; держатся ли `LaunchOptions` у
  Steam-игры; запуск Bloodborne-сессии (после второй спеки) даёт `crash` на 4 GB.
