# Витрины партнёров: разный дизайн на разных доменах

Дата: 2026-11-16. Статус: черновик на согласование.

## Зачем

Продукт будут продавать через партнёров. Первым идёт Билайн (старый сайт — beeplaycloud.ru), за ним
появятся другие. Каждому партнёру нужна своя «витрина»: свой лендинг, логотип и акцентные цвета внутри
приложения, а отдельные страницы партнёр может попросить переделать сильно. Игровые серверы, база,
аккаунты и оркестратор общие для всех.

Монетизация у партнёров разная. У Билайна будет только их подписка, биллинг на их стороне, к нам
придёт событие «оплачено» (вход по СМС и приём события — позже, не в этой задаче). Владелец: «пофиг,
как пользователь получил ту или иную подписку, главное, что она у него есть и отображается в ЛК».

## Цели

1. Понятие **витрины** (`brand`): `gamecrate` (текущая, по умолчанию) и `beeline`. Витрина
   выбирается по домену запроса.
2. **Витрина Билайна**: текущий дизайн, логотип Билайна, цвета Билайна (жёлтый `#ffc800` на тёмном
   фоне; с beeplaycloud.ru также тёмный `#28303f` и шрифт Beeline Sans), название «билайн» вместо
   «GameCrate» во всех видимых местах: `<title>`/OG/favicon, шапка, рейл, лендинг, логин, письма,
   тексты ошибок.
3. **Акцентные цвета приложения** берутся из витрины: кнопки, градиенты, свечения, активные фильтры,
   шкалы, экран загрузки, меню сессии, сцена логина.
4. **Замена страниц**: витрина может подменить любую страницу или крупный блок своей версией;
   не подменённое берётся общим.
5. **Режим монетизации** задаётся витриной:
   - `gamecrate` — как сейчас: секция тарифов на лендинге, `/app/plans`, «Докупить».
   - `beeline` — «подписка партнёра»: цен и кнопок покупки нет; на лендинге вместо секции тарифов —
     блок «Подписка оформляется в Билайне»; «Докупить» и ссылки на `/app/plans` (`PlanPanel`,
     `LoadingScreen`, `LimitWarning`) ведут на страницу с тем же текстом и текущим тарифом.
   - ЛК на любой витрине показывает действующий тариф пользователя, как бы он ни был выдан.
6. **Запуск без отдельной инфраструктуры**: тот же образ, тот же основной сервер, тот же деплой.
   Новая витрина = папка в коде + домен в настройках.

## Не цели

- Отдельные установки (своя база/основной сервер) для партнёров. Владелец: часть будущих партнёров
  может потребовать другой сервер — тогда отдельно. Сейчас только не делаем решений, которые
  это исключают (витрина — код + конфиг, без привязки к единственному `PUBLIC_URL`).
- Вход по СМС, приём события оплаты Билайна, привязка абонента — следующая задача.
- Разделение пользователей по витринам: **аккаунт один на все домены** (решение владельца).
  У пользователя/сессии/тарифа поля `brand` нет.
- Редактор внешнего вида в админке (цвета/логотип без кода).
- Светлая тема: витрины остаются тёмными.

## Анти-цели

- Витрина GameCrate после переделки выглядит иначе, чем сейчас (регресс текущего дизайна).
- Пользователь видит чужой логотип/название хотя бы на мгновение (мелькание при загрузке).
- На витрине Билайна где-то всплывает «GameCrate» или цены GameCrate.
- Добавление витрины требует трогать игровые серверы или оркестратор.

## Подходы (обсуждены)

1. **Одна сборка, витрина по домену** — выбран. Папка на витрину во фронте, свои страницы грузятся
   лениво; сервер по `Host` подставляет витрину в `index.html`. Один образ, один деплой.
2. Отдельная сборка на витрину (`BRAND=beeline`), сервер раздаёт нужный `dist` по домену — N сборок
   и дольше CI ради небольшого выигрыша в размере бандла, который ленивая загрузка и так даёт.
3. Внешний вид в админке — сильные переделки страниц всё равно требуют кода; можно надстроить над (1)
   позже, если партнёров станет много.

Отдельно обсуждали раздельные аккаунты по витринам (свой экземпляр Better Auth на витрину, уникальность
почты/Steam ID внутри витрины) — владелец выбрал один аккаунт на все домены, админ тоже один.

## Как устроено

### Реестр витрин

- Описание витрины — в коде: `apps/web/src/brands/<id>/` (тема-токены, логотип, тексты, режим
  монетизации, подменённые страницы). Общий минимум, нужный и серверу (id, отображаемое имя, `<title>`,
  описание/OG, favicon, `theme-color`, тема писем) — в месте, доступном и `apps/web`, и `apps/api`
  (например, небольшой модуль в `packages/rpc` или новый пакет — на выбор исполнителя).
- Сопоставление доменов: переменная окружения `BRAND_HOSTS`, например
  `play.beeline.ru=beeline,beeline.brofrong.ru=beeline`. Хост, которого нет в списке, — `gamecrate`.
  Домены живут в конфиге, а не в коде: стенд и прод используют разные.
- Dev: `beeline.localhost` в `BRAND_HOSTS` у dev-окружения (браузеры резолвят `*.localhost` сами).

### Как витрина попадает во фронт

- Сервер отдаёт `index.html` не статикой, а с подстановкой по витрине запроса: `<html data-brand="…">`,
  `<title>`, description/OG, favicon/apple-touch-icon, `theme-color`. Остальная статика — как сейчас.
  Так нет мелькания: CSS-токены витрины применяются по `[data-brand]` до первого рендера.
- Фронт читает витрину из `document.documentElement.dataset.brand` один раз и отдаёт её через
  контекст/модуль (`useBrand()`).

### Цвета

- Токены `--brand-*` и `--primary` в `apps/web/src/styles.css` становятся токенами витрины:
  `:root` = GameCrate, `[data-brand="beeline"]` переопределяет. Жёсткие цвета GameCrate в компонентах
  (~48 мест: `#3cc2ff`, `#3a6cff`, `#5b2fff` и их `rgb(...)`-варианты в свечениях; списки — `grep` по
  этим значениям, в т.ч. `lib/cubeAssembly.ts`, `components/login/CubeScene.tsx`, `TechFlow.tsx`)
  переводятся на токены. Вводим недостающие: акцент, второй акцент, градиент, цвет свечения, цвет
  текста на акцентной кнопке.
- Для Билайна текст на жёлтом — тёмный (контраст), не белый, как на синем GameCrate.
- Шрифт: `--font-sans` витрины. Beeline Sans — фирменный, файлы должен дать Билайн; до этого — Inter.

### Логотип и название

- Анимированный `Logo` GameCrate (`components/brand/Logo.tsx`, геометрия куба) остаётся витрине
  GameCrate. Компонент логотипа берётся из витрины; у Билайна — статичный SVG (полный и знак) без
  анимации прокрутки.
- Строки «GameCrate» (`AppHeader`, `Rail`, `LandingNav`, `LandingFooter`, `FaqChat`, `Achievements`,
  `LoginPanel`, `login.tsx`, `authErrors.ts`) берутся из витрины.
- **Официальный логотип Билайна нужно получить у владельца/Билайна.** До этого — заглушка,
  явно помеченная как временная; не рисуем «похожий» логотип.

### Подмена страниц

- Витрина экспортирует необязательные подмены по ключам (`landing`, `loginPanel`, `plansPage`,
  `landingPlans` и т.п.), каждая — `React.lazy`. Роуты/компоненты берут подмену витрины, иначе общий.
- Для Билайна сейчас подменяются только блоки, связанные с монетизацией (секция тарифов лендинга и
  страница `/app/plans`). Остальной лендинг — общий, с текстами/цветами витрины. Тексты лендинга
  (`landing/data.ts` и строки в секциях) с упоминаниями бренда — через витрину.

### Авторизация на нескольких доменах

- Better Auth один, аккаунты общие. Куки привязаны к домену, поэтому на каждом домене пользователь
  входит отдельно, но попадает в тот же аккаунт.
- Сейчас `baseURL` = `PUBLIC_URL` (`apps/api/src/auth/auth.ts`). Нужно, чтобы адреса возврата
  (OAuth callback, редиректы после входа) строились от домена запроса. Better Auth 1.7.10 это умеет:
  `baseURL: { allowedHosts: [...] }` (`DynamicBaseURLConfig` в `@better-auth/core`), базовый адрес
  берётся из хоста запроса, если он в списке. Список = хост `PUBLIC_URL` + хосты из `BRAND_HOSTS`.
  Второй экземпляр Better Auth не нужен. Проверить за прокси, что хост берётся из правильного заголовка.
- Origin для `/rpc` и мутаций (`allowedOrigins` в `apps/api/src/config.ts`) включает все домены из
  `BRAND_HOSTS`.
- Google/Яндекс/Pocket ID: callback-адрес каждого домена прописывает владелец у провайдера. Пока не
  прописан — кнопка провайдера на этой витрине не показывается; вход по коду на почту работает сразу.
  Управляется окружением, потому что зависит от домена, а не от витрины: переменная
  `OAUTH_HOSTS_<PROVIDER>` (список хостов, где провайдер включён; не задана — только хост
  `PUBLIC_URL`). Сервер отдаёт фронту список доступных провайдеров для хоста запроса (рядом с
  подстановкой витрины в `index.html` или в существующем ответе с конфигом входа).
- Письма (`apps/api/src/mail/templates.ts`): тема и текст с названием витрины, с которой запрошен код.
  Отправитель `MAIL_FROM` — общий (отдельный адрес отправителя на витрину — позже, если понадобится).

### Админка

- Один аккаунт админа работает на любом домене. Админка общая, в цвете витрины домена; отдельной
  логики витрин в ней нет (пользователи общие).

### Запуск

- Тот же образ и `compose.main.yaml`. Добавляются: `BRAND_HOSTS`, домены в `ALLOWED_ORIGINS`,
  TLS/прокси на основном сервере для домена Билайна, callback-адреса у OAuth-провайдеров.
- Стенд brofrong: поддомен для витрины Билайна, чтобы владелец посмотрел до прода.
- В `deploy/README.md` — короткий раздел «Новая витрина»: папка в `apps/web/src/brands`, строка в
  `BRAND_HOSTS`, DNS/TLS, OAuth callback.

## Мои решения (владелец отдельно не согласовывал, можно оспорить)

- Общий для web и api минимум витрины — новый пакет `packages/brands` (`@cg/brands`): чистые данные
  без React, его импортируют `apps/web` и `apps/api`. В `packages/rpc` не кладём — это не контракт RPC.
- Подстановка в `index.html`: при старте сервер читает собранный `index.html` один раз и строит готовый
  вариант на каждую витрину; на запрос выбирается вариант по хосту. Без шаблонизатора, заменой
  известных мест (`<html`, `<title>`, мета-теги, favicon).
- Градиенты у Билайна: жёлтый `#ffc800` → янтарный (около `#ff9f00`), чтобы места с градиентом не
  стали плоскими пятнами; сплошной жёлтый — на кнопках. Финальные значения проверяются глазами на стенде.
- Набор новых цветовых токенов определяет исполнитель.

## Оставлено исполнителю

- Тестами покрыть: выбор витрины по хосту, подстановку в `index.html`, отсутствие «GameCrate» и цен на
  витрине Билайна, режим монетизации, origin-проверку для доменов витрин.

## Открыто на стороне владельца

- Домен витрины Билайна (прод и стенд).
- Официальный логотип Билайна (SVG) и, если нужен, шрифт Beeline Sans.
- Куда ведёт «Подписка оформляется в Билайне» (ссылка на их страницу или просто текст).
